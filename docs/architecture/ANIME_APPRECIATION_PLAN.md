# 番剧鉴赏 / 番键会实施计划与状态

日期：2026-09-18。用户已审核 UI 并授权实现；下方保留设计和验收目标。

当前状态：无音频版已实现本机服务、原生/网页管理、原生/网页参与、持久化评分评论、历史导出与独立服务部署入口。实现和验证记录见 [番键会试用说明](../qa/banjian-implementation/README.md)。真实手机热点、锁屏保活、两小时多人验收及公网实际部署尚未验证。原 UI 稿保留在 `docs/qa/banjian-ui/`。按用户要求，音频仍暂缓；下方音频章节仅为后续候选。

## 目标与角色

入口：我的 → 设置 → 实验性功能 → 番剧鉴赏（番键会）。

- 服务端：局域网模式由 MuBangumi 所在设备运行活动服务；在线模式由配置的服务器承载并保存数据。
- 管理端：本机原生管理台或其他设备的浏览器管理活动；在线模式允许跨网络连接。
- 参与端：未安装应用的人使用网页；MuBangumi 用户扫码进入原生参与界面。原生入口平时隐藏，加入期间提供临时返回入口。
- 增加可选的电脑音频接收端：由电脑上的 MuBangumi / 桥接模块接收参与者语音、混音并输出给会议软件，独立于活动服务的托管位置。
- 上述角色可由同一设备兼任。关闭管理网页不会停止活动；服务设备关闭、断网或被系统终止会中断服务，已确认数据保留。
- 推荐首版支持 Windows、Android 作为服务端，电脑和手机浏览器作为管理端/参与端。iPhone/iPad 首版支持浏览器角色，持续后台承载服务不列为首版承诺。

## 首版范围与默认规则

1. 每台服务设备同时运行一场活动，可保存多场历史活动。
2. 管理端可创建活动、选番、调整顺序、指定当前番剧、开放/暂停/截止评分与评论、公布结果、结束活动、导出数据。
3. 选番支持 Bangumi 搜索、条目 ID，以及在本机明确选择导入的收藏/缓存条目。浏览器管理端可以完成开会流程，不要求必须在服务手机上操作。
4. 选定条目的标题、封面、简介等形成活动快照；网页脚本、样式、字体/图标不依赖外部 CDN。准备完成后，断开外网仍能开展活动。
5. 默认总评分为 1–10 分整数；不评分代表未参与，不计为零分。每个匿名参与标识、每个番剧轮次保留一份有效评分，截止前可修改。
6. 每轮允许多条短评，默认每条最多 500 字，支持评论限频与管理员隐藏。多维评分、弹幕、投票提名先不加入首版。
7. 默认参与者只看到自己的提交和活动进度；统计、评论展示由管理员开启。管理员始终可看完整活动统计。是否可查看未公布结果由服务端权限控制。
8. 有名入场、匿名评分：MuBangumi 默认使用 Bangumi 昵称并让本人确认，网页首次进入填写活动显示名。管理员可查看名单及提交状态，普通管理页面和导出不提供姓名与分数/匿名评论的对应表。为修改评分和去重，内部仍按活动参与标识关联；这是应用展示与权限层面的匿名，不承诺数据库持有人无法关联。网页自填名不是身份认证，也不宣称严格一人一票。
9. 管理端可以显示连接会话数、独立参与标识数、实际评分人数，避免把网页连接数误称为真实人数。
10. 导出 CSV（评分汇总与评论）和 JSON（完整活动记录）。基础版本共享条目信息、评分和评论，不分发视频。在线房间及语音接入分阶段加入；活动进行中不自动迁移服务位置。

## 页面设计

### 服务设备

实验性功能主页显示：启动/停止服务、网络接口与可用地址、参与二维码、管理入口、连接状态、历史活动。

本机点击「进入管理」进入原生管理台；同网电脑也可通过管理网页访问同一服务。参与二维码只包含参与入口，管理凭据单独显示和配对。原生与网页共用服务端规则和实时活动状态。

「结束活动」停止本次评分但仍可查看结果；「停止服务」关闭网络服务，二者明确分开。

### 管理网页

- 活动准备：名称、番单、顺序、评分/评论规则。
- 现场控制：当前番剧、开关评分/评论、切换轮次、公开结果、结束活动。
- 数据后台：逐番人数、均分、分布、全部评论与隐藏状态；支持导出。
- 多个管理页面共享服务端状态；写操作携带版本，冲突提示重新读取，避免覆盖其他管理员刚完成的操作。

### 原生参与页与参与网页

同一个活动二维码可由 MuBangumi「扫一扫」打开原生页面，也可由其他扫码工具打开网页。扫码进入 → 确认/填写活动显示名 → 等待开始 → 当前番剧 → 评分、评论 → 查看自己的提交/管理员公布的结果。

原生参与页不常驻主导航，只在扫码加入后出现；活动期间保留临时返回入口，退出后隐藏。网页与原生端共用同一协议；跨端参与身份转移列为后续扩展，首版提示固定使用一个入口。

断网时明确显示连接状态；恢复连接后同步完整状态。未确认提交保留本地待处理状态，不直接显示为已提交。

## 技术实现

- 新增独立 `anime_appreciation` 功能模块；不复用 OAuth 的 loopback 回调服务或其端口/凭据。
- Dart HTTP 服务提供打包的静态管理/参与网页与 JSON API；WebSocket 推送当前番剧、提交回执和汇总变化，带心跳及断线重连。
- 同一套浏览器管理页面服务本机和远程管理，避免维护两套规则。
- 服务事件和数据库写入在独立执行环境中处理，避免阻塞 Flutter 输入与动画；前端立即反馈操作状态。
- SQLite 独立保存活动、番单、轮次、参与标识、评分、评论、操作去重记录；运行管理会话使用单独凭据。
- 写入先落库再确认、再推送。每个请求带操作 ID，重试不重复生成评论或评分；轮次 ID 和活动版本决定提交归属。
- 断线重连优先重新获取状态快照；过期轮次、已截止或活动结束后的请求明确拒绝，保留用户文本供处理，不转投到新番剧。
- 管理接口有服务端鉴权、会话过期/撤销及失败限频；参与者不能用接口越权、修改别人的评分或获取隐藏统计。
- 局域网只暴露活动 API 与选定缓存资源，不暴露私信、Token、配置文件或任意文件路径。评论按纯文本渲染，限制长度和请求大小。
- 局域网模式面向受信任网络；普通本地 HTTP 不提供对同网监听者的加密保护。在线服务使用 HTTPS/WSS 和邀请鉴权，直接托管活动，减少对主持手机持续在线的依赖。

## 分阶段实施与交付

### 阶段 1：连接与生命周期验证

先做最小服务原型：Windows 和 Android 开服务；本机与另一设备打开测试管理页、参与页；实时广播一条状态。

验证 Wi-Fi、手机热点、地址选择、端口占用、Windows 防火墙、Android 局域网权限和前台服务。热点由用户通过系统设置开启，应用识别连接地址。

Android 前台服务需选择与实际行为匹配的服务类型和权限，运行期间有可见通知及停止入口。测试切后台与锁屏；不承诺系统强杀/强制停止后仍继续服务。

如学校/公共 Wi-Fi 启用客户端隔离，同网设备也可能互相无法连接；提供连通性诊断与换用热点的指引，不用一个“启动成功”替代实际可达性检查。

**交付：** 两设备互访与实时同步证据、平台支持边界。通过后再进入完整实现。

### 阶段 2：活动与数据核心

实现活动状态机、番单快照、匿名会话、评分/评论写入、请求去重、管理权限和持久化恢复。

**交付：** 可测试的后端、接口与数据格式；覆盖并发评分、重复评论、截止边界、越权、重启恢复。

### 阶段 3：服务端入口与选番

增加实验性功能入口，接入搜索/条目 ID/本机选定收藏导入、离线资源准备、服务状态和两类入口分享。

**交付：** MuBangumi 内可启动、停止、恢复活动服务，显示真实可用地址。

### 阶段 4：浏览器管理端、原生参与端与网页参与端

先完成 MuBangumi 原生参与页、网页参与页与电脑管理页原型供审核，再接入实时 API；加入显示名登记、匿名评分权限隔离，并补齐同机管理、小屏管理和大屏结果展示。

**交付：** 完整的创建活动→选番→扫码→评分评论→公布结果流程。小屏、大字号、横竖屏可用。

### 阶段 5：异常恢复与导出

完善断网重连、热点变化、重复提交、过期轮次、管理端重开、服务重启、历史回看、CSV/JSON 导出。

**交付：** 可恢复的完整活动记录与操作错误提示。服务地址变化时重新展示二维码，并明确旧链接可能失效。

### 阶段 6：多人实测与本地试用版

模拟客户端压测，同时使用真实手机与电脑交叉测试。Android 保活不能只靠模拟器判断。

**验收目标（待实测，不是已达到）：**

- 手机开服务、电脑管理、其他手机评分；电脑开服务并本机管理两种组合均跑通。
- 服务容量目标为 50 个参与客户端同时在线、连续运行 2 小时；正常局域网下 95% 的评分/评论更新在 1 秒内出现在管理页，记录设备与网络条件。手机热点实际可接入多少设备另行实测，不把服务容量等同于热点连接上限。
- 重复提交不增加同一轮的评分人数，不重复生成相同操作 ID 的评论。
- 服务端重启后，所有已确认提交的数据可恢复；未确认请求保持待确认，不伪报成功。
- 参与端无法访问管理操作与未公开结果；对普通管理者不展示个人分数映射，评分展示标识与入场显示名分开。
- 管理页关闭/重开不结束活动；评分截止期间的迟到请求不会落到下一轮。
- Android 前后台与锁屏、外网断开仍可进行活动；网络本身变化时能够明确提示并恢复连接。

## 代码核查依据

当前可复用：`SettingsPage`、`BangumiApi.searchSubjects`、收藏条目模型、二维码生成、SQLite 与本地导出习惯。现有 `HttpServer` 仅用于 OAuth loopback 回调；没有实验性功能页、局域网房间服务、浏览器活动页面及 Android 托管服务，因此不能仅靠添加一个设置按钮完成。

平台参考：[Android 前台服务类型](https://developer.android.com/develop/background-work/services/fgs/service-types)、[Android 局域网权限](https://developer.android.com/privacy-and-security/local-network-permission)、[Apple 局域网隐私](https://developer.apple.com/documentation/technotes/tn3179-understanding-local-network-privacy)。具体权限随项目目标 SDK 与实际平台行为核对，不预设所有手机都能无限后台运行。


## 后续阶段：在线托管与语音接入

### 在线托管

- 局域网和在线模式使用相同活动协议；创建活动时选择本机或远程服务器作为唯一数据来源。
- 云端提供 HTTPS API、WSS 状态同步与邀请入口；加入/管理认证分离，配置请求限频及活动数据保存策略。
- 手机、电脑上的 MuBangumi 可以只是管理/参与客户端；云端活动不依赖主持手机保持运行。

### 语音目标与技术路径

参与者手机麦克风 → WebRTC → 主持电脑音频接收/混音模块 → 虚拟音频设备 → 腾讯会议麦克风输入。

活动服务负责加入、权限、信令和控制；实时媒体走独立低延迟通道，不进入评分/评论的持久化命令队列。局域网优先直连，跨网根据网络情况配置 TURN 中继；服务器若只运行活动 HTTP API，并不自动具备语音中继能力。

Windows 电脑需要运行 MuBangumi 音频模块或配套桥接程序。浏览器管理页可以控制该模块，但仅打开管理网页不保证能把音频注入系统麦克风。第一版优先适配已安装的虚拟音频设备（候选 VB-CABLE），提供设备选择与测试向导；不从零编写、签名和分发音频驱动。驱动安装与授权条件在实际实施前单独核对，不自动安装或擅自更改系统默认音频设备。

### 语音分步实现

1. **单路原型：** Android 原生参与端主动授权麦克风、按住说话；Windows 接收并通过选定输出设备播放。
2. **会议桥接：** Windows 选择虚拟设备作为输出，腾讯会议选择其对应录音端点；由另一台会议终端验证实际听到声音。
3. **管理控制：** 参与者申请发言，主持人允许/静音/结束通道；显示每路电平、连接状态、音量和总音量。管理员不能代替参与者授权或偷偷启动麦克风。
4. **多人调音：** 优先验证最多 4 路同时发言，并支持可选的主持人本机麦克风混入；加入限幅、噪声处理、设备切换和断线静音。该容量与评分端 50 人在线目标分开。
5. **网页与跨网：** 网页采音需要安全上下文，不能保证普通 HTTP 局域网 IP 页面调用麦克风。验证受信任 HTTPS 与在线入口；跨网增加 TURN 凭据、限额及弱网测试。

首版默认按住说话、不录音、不向所有参与者回传腾讯会议声音；监听输出和会议输入路由分开，避免会议声音回灌形成回声。参与者音频名使用入场显示名，评分匿名规则不变。

### 语音验收

- 从手机讲话到腾讯会议另一端实际听到，完整链路可重复演示。
- 受控局域网内手机采集到电脑音频输出的 95% 延迟目标不超过 300ms；腾讯会议自身及远端网络延迟单独测量，不混为同一指标。
- 切换设备、拒绝麦克风授权、撤销发言权限、手机断网、接收电脑离线时，不出现持续噪声、串音或旧音频积压重放。
- 多路音量可独立控制；测试本机麦克风混入、耳机监听及回声回灌情形。听感、清晰度和稳定性须用真实设备验收，不能仅凭编译通过承诺。

参考：[WebRTC TURN](https://webrtc.org/getting-started/turn-server)、[Flutter WebRTC](https://github.com/flutter-webrtc/flutter-webrtc)、[VB-CABLE 路由说明](https://vb-audio.com/Cable/)、[腾讯会议设备选择](https://meeting.tencent.com/support/topic/1728/index.html)、[网页麦克风安全上下文](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia)。
