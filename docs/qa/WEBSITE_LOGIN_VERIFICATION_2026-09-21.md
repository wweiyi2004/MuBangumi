# 网页有头像但聊天、小组仍验证失败：排查与修复

## 用户现象

Android 与 Windows 均出现：在应用内“补充账号验证”页面已经看到网页账号头像，但应用仍报告验证失败。

## 已确认的代码问题

1. 登录页成功与应用核验使用了两个不同的请求环境。旧实现只捕获 WebView Cookie，随后用独立 Dio 请求首页推断账号；Dio 默认发送 MuBangumi User-Agent，浏览器使用自己的 User-Agent。独立请求遇到网页挑战、网络错误或账号导航解析失败时，已经登录的网页也不能使核验完成。
2. 自动捕获在核验完成前记住 Cookie 字符串。首次失败后，只要 Cookie 不变，页面完成登录或网络恢复也不会自动再次核验。
3. 主动点击“补充验证”与普通业务请求共用了“不因临时网络失败弹登录页”的策略；在 unavailable 状态下主动操作也只能看到提示，无法进入网页恢复。
4. 新 Cookie 的独立核验临时失败时，原实现仅更新内存，没有保留未核验快照；重新打开或重启容易退回旧记录。
5. 工作区已有一批 2026-09-19 的减少重复核验修改，但尚未进入已发布 2.3.1 安装包。此次修复一并纳入相关变更，排除其他界面、收藏与缓存工作。

这些是可由代码与回归测试确认的缺陷。未读取真实 Cookie，也没有真实账号的 HTTP 抓包，因此不能声称已证实用户现场的具体 Cloudflare 规则或网络原因。

## 修复后的核验规则

- 从当前应用持有的 WebView 读取官方账号导航（`#headerNeue2`、`#badgeUserPanel`、`#dock`），不采集私信或话题正文。读取前后检查认证 Cookie 和导航状态保持稳定。
- 只接受 HTTPS `bgm.tv`、默认 HTTPS 端口、无 URL 用户信息且不处于退出页面的浏览器证据，并与本次 Cookie 的认证标识绑定。
- 仍使用严格的官网导航解析器解析用户标识，与当前 API 已验证账号的 UID / 用户名比较；陌生域名、正文作者头像、歧义身份、换号和 Cookie 变化均不能获得授权。
- 已明确识别当前网页账号时，不再额外依赖一次独立 Dio 首页请求完成登录。没有可用浏览器证据时，继续使用原 HTTP 核验。
- 保存捕获时的浏览器 User-Agent，身份探测、私信读取/提交、小组网页表单读取/提交均沿用该 User-Agent。公共 API 的身份查询不携带网页 Cookie。
- 只缓存自动核验成功的 Cookie；失败可以重试，同一组 Cookie 的自动尝试间隔至少 5 秒，新 Cookie 不受旧失败节流限制。
- 用户主动修复允许进入网页登录页；普通业务请求遇到临时错误仍保留登录，不自动弹窗打断操作。
- 临时核验失败的 Cookie 以未核验状态保存，供恢复后重试。明确错号不覆盖此前正确的持久会话。
- 登录绑定可跨重启复用，明确过期、错号或挑战失败会撤销；认证 Cookie 过期时，匿名 Cookie 不能沿用旧绑定。

## 验证

- 在基于 `origin/main` 的独立工作目录验证，只带入本次登录与此前相关核验修复。
- 新增 WebView 平台通道回归：网页包含已登录账号，独立 HTTP 探测器恒定失败，仍能核验并保存正确账号；持久化浏览器 User-Agent。
- 新增首次失败后同 Cookie 自动恢复、主动恢复入口、跨账号拒绝、浏览器导航来源及 Cookie 绑定、待核验快照重启恢复、数字用户名、请求头安全、私信及小组 User-Agent 复用等测试。
- 全量 `flutter test --no-pub`：**1,202 项通过**。架构检查：**249 个 Dart 文件，无依赖环或反向依赖**。
- 测试中的请求通过替身拦截，没有向真实好友发送私信、发帖、入组或操作真实账号。

## 交付边界

此报告记录源码修复与自动化验证；真实账号的两端回归需要运行包含修复的程序。

主线已含先前更新器的 Android 原生安装目录变更。因此不能直接将整个当前主线当作旧 `2.3.1+4029` 的纯 Dart 补丁，也不应使用 `--allow-native-diffs` 强行跳过兼容性检查。若走旧基线热更新，应从该基线单独提取认证修复，先验证 Android 和 Windows 补丁兼容性；否则发布完整新版本。
