# 统一账号与登录改造清单

2026-09-17：本清单的统一账号与小组二维码代码已实现，见 [实现与验证记录](../qa/UNIFIED_ACCOUNT_AND_GROUP_QR.md)。下文保留改造前的核查与验收目标。

日期：2026-09-17。此文为代码核查后的实施范围，本轮没有修改登录逻辑或操作真实账号。

## 目标与用户体验

一个主登录入口、一个账号状态入口，底层继续分别管理 OAuth / Access Token 与官网 Cookie。

正常流程：点击“登录 Bangumi” → 应用内完成官网登录及授权 → 校验 API 身份 → 保存 API 凭据 → 核对捕获的网站会话是否属于同一个用户 → 返回应用。

API 身份已验证时即可进入应用。网站会话缺失、过期或暂时无法核验，只影响需要该会话的功能，不应导致收藏、进度和本地内容一起退出。

设置只保留一个“Bangumi 账号”入口。手动 Token 与自定义 OAuth 配置放在高级选项；普通页面不要求用户理解两套凭据。

## 核查发现的缺口

1. `WebsiteSessionState.isSynced` 目前主要表示“有未过期的疑似会话 Cookie”。不等于服务器接受该会话，也不等于已核对当前用户。
2. `WebsiteCookie.looksLikeSession` 使用较宽泛的名称判断；仅有主题、挑战或其他非认证 Cookie 时，不能据此显示“登录正常”。认证候选检查需要收紧，最终仍以服务器身份核验为准。
3. 单独官网登录保存后，`CommunityWebScreen` 会回调“保存成功”，尚未由统一入口确认网站身份。其 `sameAccount()` 校验的是应用账号没有切换，并非网页实际登录的账号相同。
4. OAuth 成功保存 Cookie 时，当前分支直接将 API 用户 ID 写为 `verifiedUserId`。需把来源证据及 Cookie 版本绑定收紧，避免只凭“API 成功 + 捕获到 Cookie”就认定两者身份一致。
5. 网站身份检查目前主要服务于私信草稿。小组网页写入 `_requireWebsiteCookieHeader` 尚未复用同等身份门禁。
6. 网站 401、跳回登录页等主要在各业务里报错，官网会话的全局状态可能仍显示“已保存”。
7. 私信、设置、小组各自打开补登录页面，缺少统一的并发去重和返回上下文管理。
8. Windows 浏览器 Cookie 清理采用后台尽力执行，失败只记日志。退出和下一次登录之间还需更明确的清理结果与重试状态，避免静默复用残留会话。

## 需要改的模块

### 1. 统一状态与协调层

新增账号协调层（建议 `features/auth/application/account_access_controller.dart`）和只读组合状态。

- API 登录仍以 `SessionController` 为主，不再创建第二个主账号来源。
- 官网状态明确区分：缺失、待核验、核验中、可用、已过期、账号不一致、需要验证、网络暂不可用。
- 组合状态对外提供业务能力，例如可调用 API、可读写私信、可打开需登录的小组页面。
- 同一账号的官网核验合并为一次请求；补登录窗口也只打开一个。
- 统一使用应用账号代次 + 认证 Cookie 标识 + 预期用户 ID 约束回调，拒绝晚到的旧结果。
- 保留验证码 / Cloudflare 校验与登录失效的区别，不把挑战页一律视为退出登录。

### 2. 官网身份核验与凭据绑定

新增通用官网身份核验服务，复用现有网页身份解析能力，将私信专用核对逻辑提取为公共能力。

- 网站核验请求只带候选 Cookie，不能混入 API Bearer Token，否则会把 API 身份误当成 Cookie 身份。
- 将官网识别到的用户标识解析为稳定的用户 ID，与 API 的 `/me` 身份比对。
- 捕获 Cookie 后先核验再标记为“可用”；认证 Cookie 改变时使旧校验失效。
- 断网时保留待核验记录，不将其作为已验证的网站写入凭据。
- 账号不一致时保留正常 API 登录，阻止有歧义的网站读写，提示登录同一账号；不能因此切换整个应用账号。
- Cookie 捕获、身份核验、持久化必须归属同一次登录代次。补登录失败不能覆盖另一份仍可用的已核验会话。

主要影响：`website_session.dart`、`website_session_controller.dart`、`website_cookie_bridge.dart`、`SessionController._authenticate`。

### 3. 登录与设置界面

- `auth_screen.dart`：主按钮统一文案，保留高级 Token / 自定义 OAuth 入口；显示授权与验证进度。
- `settings_page.dart`：用“Bangumi 账号”卡片替代独立的网站登录管理入口；详情内显示哪些功能可用、是否需要补登录。
- `website_login_screen.dart`、`community_page.dart`：从“保存 Cookie 即返回”改为统一核验完成后返回；错误信息说明是网络、过期、挑战还是账号不一致。
- 已完成的个人主页布局保留。账号入口放在设置，不重新把登录工具堆回“我的”。

### 4. 业务统一接入

- 私信列表、会话、发送：接入统一的网站能力检查，复用同账号会话和身份结果。
- 小组加入 / 退出、官网回退发帖和回复：使用同一会话检查，移除只判断存在 Cookie 就放行的分散逻辑。
- Token 客户端继续复用已有自动刷新回调，不能因为网站会话过期而清空 API 登录。
- 业务识别到明确的会话失效后反馈给协调层，其他页面随之更新。
- 补登录完成后返回原页面、恢复接收人 / 小组 / 草稿；不自动重发结果不明的写请求。

主要影响：`pm_service.dart`、`community_service.dart`、`pm_page.dart`、PM 会话 / 写信页、`community_group_screen.dart`。

### 5. 续期、退出与迁移

- 保留现有 Token 并发刷新合并及 generation 防护，扩大测试覆盖两种凭据同时变化的情况。
- API 401 与网站失效分别处理；网络超时、服务器 5xx 不删除有效凭据。
- 个人 Token 没有 refresh token 时，提示重新授权或在高级选项替换，不进入刷新循环。
- 退出先让应用内身份失效、使在途请求失效，再串行清理持久化与 WebView Cookie；清理失败可追踪、可重试，且不静默复用旧会话。
- 兼容现有 Token v2 与 website session v1。有效 Token 不强制重新登录；已有官网会话先进入待核验状态，核验通过后升级身份绑定。
- 不读取或保存账号密码，不在日志中输出 Token、Cookie、授权 code。

### 6. 构建与真实平台验证

- 复用现有发布脚本，确保面向用户的包包含正确 OAuth 应用配置。普通 `flutter build windows --debug` 未传配置时，不能据此验收“一键登录”的最终体验。
- 分别验证 Windows WebView2、Android 和 iOS 的 Cookie 捕获、注入、HttpOnly、过期及退出清理行为。
- 实际网页登录 / 授权由用户完成；真实业务写入单独验收，不以模拟测试代替。

## 验收清单

1. 新安装首次正常登录，完成一次官网授权即可使用 API；网站会话完成核验后可用私信。
2. Token 正常而 Cookie 过期：应用保持登录，收藏可用，私信引导补登录。
3. API 和网站为不同账号：明确提示不一致，不以错误账号发送私信或进行小组操作。
4. 仅有主题 / 挑战 Cookie：不能显示已核验登录，也不能作为网站写操作凭据。
5. 多个 API 请求同时失效：只刷新一次 Token；多个页面同时需要官网会话：只核验一次、只打开一个补登录窗口。
6. 断网、超时、5xx：保留可信登录与缓存，不误退出；联网后可以重试。
7. 登录 / 核验 / 保存期间退出或换号：旧回调不能恢复旧身份或覆盖新凭据。
8. 补登录中取消：返回原页面，接收人、讨论对象及草稿保留。
9. 写请求超时：不自动重复发送、发帖或发布日志。
10. 清理失败及旧版会话迁移：有明确状态和重试路径，不静默恢复旧账号。

## 与布局及二维码的衔接

- 布局方案已获用户认可；当前代码已有新导航和个人主页，Windows 调试构建曾因正在运行的旧程序占用 DLL 而未完成替换。它与账号改造分开验证。
- 小组二维码仍未实现。后续统一扫一扫可识别好友 / 小组，展示详情，再使用本方案的网站会话能力处理加入；二维码不会自动加入或绕过小组限制。
- 优先顺序：统一官网状态与身份核验 → 业务接入及错误回传 → 登录 / 设置入口 → 迁移和平台验收 → 接入小组扫码。
