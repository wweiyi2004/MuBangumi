# 自己创建或管理的小组：角色专项修复

用户明确问题集中在创建/管理的小组后，本轮进一步核对官方角色定义和管理列表调用。

官方 [GroupMemberRole](https://github.com/bangumi/server-private/blob/e5340036c228e887185438feb579d8384dbf3954/lib/group/type.ts#L21) 的取值为：访客 -2、未加入 -1、普通成员 0、创建者 1、管理员 2、被限制 3。官方管理列表 mode=managed 筛选创建者和管理员；客户端不应自行交换这些值。

## 发现与修复

- 原“管理员”预览只请求 role=1，实际上只取到了创建者。现在并行请求 role=1 和 role=2，合并后按用户 ID 去重；其中一项失败时保留另一项，并提示部分加载失败。
- 原模型没有保留当前用户的角色。现在保留官方角色，创建者/管理员分别显示“创建者 · 管理”与“管理员 · 管理”；入口打开官网小组管理页面，不再把管理者入口称为“退出小组”。
- 前一轮已将成员记录与加入日期分开，本轮进一步区分活跃成员和访客/被限制记录。日期缺失不影响创建者/管理员身份，但角色字段没有成员身份依据时不授予管理身份；被限制状态不提供发帖入口。
- 官方列表在匿名状态下可能忽略 managed/joined 筛选而返回公开列表。客户端现在在请求之前、响应返回及缓存读取时检查所需授权，避免把全站小组误显示为“管理的小组”。

## 保留的约束

管理身份由 API 返回的当前账号 membership 记录确定，不因历史 creatorID、昵称相同或接口失败而假定用户有管理权限。发帖、回复、加入/退出仍由服务端做实际权限校验；上游成员参数顺序错误的兼容处理保持有效。

没有发送真实管理请求、改变成员权限、加入/退出小组或发布测试帖。组件测试覆盖创建者和管理员在手机宽度下的身份与发帖入口；合成接口测试覆盖两个管理角色、部分失败、非活跃角色、授权丢失和过期响应。旧实现上的 6 个新增角色/请求案例失败，修复后通过。

最终验证使用 `tool/verify_all.ps1 -Mode Full`，以生成的源码指纹报告为准。真实管理账号仍需在修复版核对显示和官网入口。
