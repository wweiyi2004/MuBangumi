## 3. 确认的问题

### F1 · P1 · 旧账号加/删好友请求可按新账号凭据重试【本轮已修复】

位置：`lib/core/network/community_service.dart` 的 `_putJson()`、`_deleteJson()`，约第 1931、1964 行。

原实现没有像 `_nativeWrite()` 一样固定并检查账号修订号。复现时先发出账号 A 的请求，切换为 B，再返回 A 请求的 `TOKEN_INVALID`。原代码会刷新当前凭据并发出第二次写入；捕获到的授权顺序为 `[A, B]`。这可能让 B 执行 A 发起的加/删好友操作；共享这些方法的贴贴等操作也存在同类边界。

本轮在刷新前和刷新后分别检查账号归属，防止迟到的 401 触发其他账号的刷新和重试。新增回归覆盖 PUT/DELETE × 迟到 401、刷新中切换、退出、同账号正常续期；同账号续期仍可正常重试。

证据：[修复前输出](full-review-2026-09-22/account-retry-before.txt)、[永久回归](../../test/community_account_retry_test.dart)。所有请求均为模拟，没有操作真实好友关系。此项说明重复的请求辅助方法容易在保护规则上发生偏差，是后续网络层整理的直接依据。

### F2 · P2 · 番键会首次打开本地数据库失败后无法重试恢复【历史发现，后续已修复】

位置：`lib/features/anime_appreciation/room_storage.dart:77`。

`_open()` 将开库 Future 放进 `_opening`，但失败后没有清空。第一次目录查询或数据库打开暂时失败后，即使外部条件恢复，后续 `read()` / `write()` 仍返回原来的失败 Future。

隔离复现让路径提供器只失败一次、之后返回有效的内存数据库路径。第一次失败符合预期，第二次读取仍抛出首次错误。用户需要重建存储对象或重启才能脱离该状态；并未证明数据库数据被删除。

修复要求：并发调用继续共享一次开库；失败时清理 `_opening`，允许下一次尝试；同时检查失败开库是否留下错误的 schema 初始化标志。加入“首次失败→环境恢复→读取成功”和“并发首次读取只开库一次”回归。

证据：[独立复现用例](full-review-2026-09-22/room_open_repro_test.dart)、[原始失败输出](full-review-2026-09-22/room-open-repro.txt)。

### F5 · P2 · 网站开发/构建依赖存在已知安全告警【历史发现，后续已治理并纳入重复审计】

使用 npm 官方 registry 完成审计，得到 **23 条受影响包记录：16 high、6 moderate、1 low，0 critical**。这是依赖包及传播链的记录数量，不是 23 个独立漏洞，更不表示线上已遭入侵。

`--omit=dev` 的生产依赖分类结果为 0 条；但 vinext、Vite、Workers 和 React Server Components 工具在本项目列于开发依赖，仍会用于开发、构建及可选 SSR 输出，不能只看 production 分类就结束治理。

示例：锁定的 `react-server-dom-webpack@19.2.6` 命中服务端函数拒绝服务公告；Vite 8.0.13 命中 Windows 开发服务器文件访问限制绕过公告。当前 GitHub Pages 发布的是静态文件，服务端漏洞的暴露条件应与开发机、CI 和可选 Workers 部署分别判断。[React 公告](https://github.com/advisories/GHSA-wx67-qw84-cm4g)、[Vite 公告](https://github.com/advisories/GHSA-fx2h-pf6j-xcff)。

建议按框架兼容组合处理直接依赖与传递依赖，分批更新锁文件，并同时运行类型检查、SSR、静态构建和交互测试。审计工具对 drizzle-kit 给出的候选包含版本回退，不能把自动建议直接当作可用升级方案。

最初默认 npm 镜像不支持安全审计接口；本轮明确切到官方 registry 后才得到有效结果，没有将接口失败视为“没有漏洞”。证据：[审计 JSON](full-review-2026-09-22/npm-audit.json)。

Dart 的 `pub outdated` 还列出了 17 个存在可选更新的直接依赖，详见 [版本清单](full-review-2026-09-22/dart-outdated.json)；版本落后本身不等于安全漏洞。Android 构建同时提示 6 个插件仍使用 Kotlin Gradle Plugin，应在未来 Flutter 基线升级前完成兼容验证。

### 5.1 一个统一的验证入口

建议新增 `tool/verify_all.ps1`，先检查工具版本与依赖环境，再按模块执行命令，最后输出机器可读结果和失败步骤。快速检查与包含原生构建的完整检查分开，避免日常修改每次都承担所有构建成本。

CI 应以路径选择模块，但共享协议、依赖锁文件、原生插件和发布脚本变更必须触发相关模块。网站增加显式 `typecheck` 脚本；Python 在受控虚拟环境安装锁定依赖。依赖与 Actions 更新可按周自动创建 PR，再由构建与回归验证。[Dependabot 配置参考](https://docs.github.com/en/code-security/reference/supply-chain-security/dependabot-options-reference)。

每次 PR 至少回答：影响什么用户行为、如何复现、覆盖哪个失败路径、是否涉及原生代码/数据库/发布兼容。配置、凭据、数据集和本地数据库继续保持隔离。

### 5.2 把 Android 登录验收作为发布必需项

建立固定场景：首次 OAuth、已有会话冷启动、网站会话到期、官方网页挑战、弱网后重试、前后台切换、切换账号时旧请求返回、私信发送回执丢失、小组网站通道回退。

Flutter 的集成测试可在设备或模拟器上运行，用于覆盖真实插件参与的应用流程；官方网页人机验证保留人工完成步骤，并在受控测试账号和测试小组中验收。[Flutter 集成测试文档](https://docs.flutter.dev/testing/integration-tests)。

建议的硬性验收条件：跨账号写入为 0；不确定 POST 自动重发为 0；暂时网络/存储失败不删除有效凭据；恢复后不要求重启应用；失败和取消后草稿可恢复。性能阈值先在代表性 Android 设备的 Profile/Release 包上建立基线，不用桌面 Debug 数据替代。

### 5.3 沿职责拆分，保留现有技术栈

优先收拢账号请求上下文与重试策略，再把社区 P1 传输、经典网页表单、解析和业务操作拆开。不同业务继续区分：GET 可有限重试；目标状态写入需要账号保护；私信等追加操作遇到不确定结果必须核对；番键会使用操作回执去重。

对每种异步入口采用统一测试模板：并发合并、首次失败后重试成功、旧成功/旧错误迟到、取消、退出和重新登录。F1 与 F2 都说明这类规则不能仅靠单个开发者记住。

继续利用现有应用层、Repository 和 Provider 注入，不做全仓框架迁移。Riverpod 大版本升级单独安排兼容迭代。Flutter 官方架构指南也将职责分离、服务和数据访问边界作为组织原则；具体拆分应由本项目的变更风险决定。[架构指南](https://docs.flutter.dev/app-architecture/guide)。

### 5.4 让现场问题可以诊断

复用现有有界诊断模式，为登录/私信/小组记录：流程阶段、请求编号、账号代次、HTTP 状态、重试次数、耗时、浏览器主要版本、安装基线和补丁号。导出前允许用户查看。

不记录 Token、Cookie、表单验证码、私信正文或完整网页。用户界面继续使用“网络暂不可用”“需要网页验证”“账号已变化”等可操作提示；协议和内部状态放在诊断页面。

### 5.5 发布与数据兼容形成固定记录

将普通包与 Shorebird 补丁统一记录为：源码 commit、dirty 状态、平台/架构、安装基线、补丁号、Flutter/引擎版本、依赖锁哈希、产物 SHA-256、测试结果和符号位置。发版从可重建的工作区进行，凭据值不进入记录。

CI 明确最小权限，第三方 Actions 固定到完整提交哈希并定期更新；同时维护不可变版本的验证结果。GitHub 官方将完整 SHA 固定作为降低 Action 被替换风险的措施。[安全使用参考](https://docs.github.com/en/actions/reference/security/secure-use)。

每次 SQLite/备份格式变更都扩充前一版与较早版的迁移样例，涵盖中断、重复恢复和账号归属。现有崩溃恢复与备份测试应保留；番键会的 50 客户端短时回环测试不能替代实际 Wi-Fi、Android 锁屏和长时间活动验收。
