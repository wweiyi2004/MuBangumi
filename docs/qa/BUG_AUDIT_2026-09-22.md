## 项目结构

- 主应用：Flutter / Dart，版本 `2.3.1+4029`；Riverpod 负责状态和依赖装配，目标平台为 Android、Windows、iOS。
- `lib/screens`、`lib/widgets`：界面；`lib/state`：会话和功能控制器；`lib/features`：逐步拆出的收藏、同步、详情、私信、新番表和番键会功能。
- `lib/core/network`：Bangumi OpenAPI、P1、网站 HTML、RSS 等适配；`lib/core/storage`：SQLite 队列与快照；认证凭据另有安全存储。
- 收藏写入采用先入持久队列、再更新本地界面、后台补传的流程；私信和番键会分别使用适合自身业务的队列。
- `packages/banjian_server`：可嵌入应用或独立运行的 Dart HTTP / WebSocket 服务，SQLite 保存活动数据。
- `website`：React / Vite / vinext 项目主页；`native-android`：已冻结的 Kotlin 原型；`tool`：发布、维护及推荐数据工具。

## 已确认缺陷

### F3 · P2 · 停止上传单条修改会删除整个账号的离线收藏快照

位置：`lib/features/collection/application/collection_editor.dart:364`。

`discardBlockedMutation()` 在删除一条未被后续操作取代的失败记录后，调用 `clearCollections(username)`。该方法删除的是整个账号的收藏快照，并非仅使该作品的修改失效。

复现：

1. 保存含动画 A 和书籍 B 的收藏快照。
2. 让 A 的一条章节修改进入 blocked 状态。
3. 对这条记录执行“停止上传”。
4. 重新读取收藏快照，结果为 `null`，与 A 无关的 B 也已消失。

界面之后会尝试刷新，但刷新失败时不会补回该快照。冷启动通过 `session_controller.dart:312` 读取这份快照；因此在断网重启的条件下，原有收藏不能恢复，除非之后联网重新获取。服务器收藏不受影响，账号凭据也没有被删除。

建议：保存服务器基线与本地覆盖层，撤销单条覆盖时只处理对应作品；至少保留其他作品和快照的完整性元数据。不得以清除全账号快照代替单条撤销。修复后覆盖“撤销 → 刷新失败 → 离线重启”的完整路径。

### F1 · P2 · 点击“下一集”覆盖全类型章节快照，特殊章节离线消失

位置：`lib/features/collection/application/collection_editor.dart:434`、`:450`。

`markNextEpisode()` 调用 `getEpisodeCollections(subjectId)`，其默认 `episodeType = 0`，仅请求本篇。随后把这份列表写入与全类型章节共用的缓存键。`SnapshotCache.writeEpisodeCollections()` 是整份替换，不会合并之前的 SP / OP / ED。

复现：

1. 通过详情加载路径缓存本篇、SP、OP 三个章节，ID 分别为 101、102、103。
2. 在线执行一次“下一集”。
3. 再读取离线快照，只剩 `[101]`，102 和 103 被丢弃。

用户此前已打开并缓存的特殊章节，在断网后无法显示和继续操作。在线重新加载全部章节可以恢复；服务器章节记录不受影响。

建议：本篇刷新只替换快照中的本篇部分，保留其他类型；或区分全类型和按类型缓存，并在读取时合并。测试应同时断言特殊章节及其原有观看状态被保留。

### F2 · P2 · RSS 刷新期间解除绑定，迟到结果仍产生新提醒

位置：`lib/state/rss_controller.dart:388`、`:436`；写入检查位于 `lib/core/storage/rss_store.dart:120`。

`_refreshSource()` 在请求前捕获绑定列表，网络返回后继续使用该旧列表匹配。`unbind()` 只删除绑定，没有使这次匹配失效。SQLite 插入事务只确认 RSS 源仍存在，没有核对绑定是否仍然有效，因此删除源的既有保护不能覆盖解除绑定。

复现：

1. 为作品 Anime 添加绑定并开始刷新，暂缓网络结果。
2. 完成解除绑定，确认数据库中的绑定已为空。
3. 返回一条匹配旧绑定的 `Anime 01`。
4. 刷新结束后未读数为 1，期望为 0。

此处讨论的是解除绑定后新写入的提醒，不是要求删除之前已有的历史提醒。自动刷新在前台运行，解绑入口也没有因刷新而禁用，因而该交错可由正常操作触发。

建议：给绑定增删改维护修订号，并在网络返回后使用有效绑定重新匹配；最终插入时在同一事务中校验绑定身份和修订，覆盖检查后、写入前再次解绑的窗口。
