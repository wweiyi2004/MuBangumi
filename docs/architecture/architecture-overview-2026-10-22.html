当前存在的跨层调用：部分页面直接访问 CommunityService 等服务，并自行管理请求与界面状态。时间线页面就是优先抽离控制器的对象。
为什么称为“混合结构”？

顶层仍保留 screens、state、widgets 等按技术职责划分的目录；features 内又按收藏、社区、私信等功能组织 application、domain、presentation。已有应用逻辑拆分，但各功能的迁移程度不同。Riverpod 用于状态订阅与依赖提供，一些控制器通过 ChangeNotifier 或回调发布结果。

03 / BOUNDARIES

三个独立的身份边界

API IDENTITY

API 凭据

OAuth / Access Token，供相应 API 请求使用；维护令牌续期与账号归属。

WEBSITE IDENTITY

网站会话

Cookie、WebView 与网站身份校验，支撑网站专属能力。

ROOM IDENTITY

番键会凭据

独立的活动参与和管理凭据，服务于番键会协议。

重构时保持明确的账号归属：切换账号后丢弃旧响应；社区 P1 写入复用 CommunityWriteClient；结果不确定的私信 POST 不自动重放。

04 / EVOLUTION

重构重点：先拆职责，再调整目录

优先
社区服务 · 2,487 行

CommunityService 汇集多类社区业务、缓存和账号保护。

先抽离时间线读取逻辑，再按小组、日志、目录等职责拆分；保留共享身份上下文与写入客户端。

优先
时间线页面 · 945 行

页面 State 管理分页、定时刷新、回复、点赞与删除。

提取独立控制器。页面处理展示与生命周期信号，控制器处理请求顺序和状态变化。

随后
收藏编辑器 · 1,124 行

章节读取、缓存、编辑、撤销和失败恢复集中。

逐步分离读取与编辑流程，保留统一的账号校验、条目串行队列和修订号。

随功能
大型界面文件

收藏统计、发现页、番键会页面。

结合实际修改提取独立展示区块；统计计算与发现请求已经有独立模块。

首轮建议范围

社区时间线的数据访问与状态管理，并补齐架构检查对 features/*/presentation 和 domain 依赖的规则。用账号切换、旧响应、分页和失败恢复测试验证行为一致。
